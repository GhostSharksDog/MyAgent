## 一、为什么 Agent 需要两种记忆

在写代码之前先把问题分清楚，因为"记忆"是个被滥用的词，两种记忆解决的是
完全不同的问题：

| | 短期记忆 | 长期记忆 |
|---|---|---|
| 解决的问题 | **上下文窗口的物理限制** | **跨会话的知识沉淀** |
| 内容 | 刚才聊了什么 | 关于用户的事实与偏好 |
| 生命周期 | 一次会话 | 跨会话持久化 |
| 写入方 | 自动（每轮成功后） | **模型主动判断** |
| 检索方式 | 时间顺序 | 语义相关性 |
| 载体 | 内存 | JSON → Redis/SQL |

与 RAG 的区别值得强调：RAG 检索的是**静态文档**（简历、岗位库），
长期记忆检索的是 **Agent 在自己与用户的交互中积累的事实**。
两者可以共用向量基础设施，但语义与生命周期完全不同 ——
把它们混为一谈会导致"用户偏好"和"简历原文"被同等对待。

## 二、短期记忆：三档策略的权衡

P1 的做法是**只把 user/assistant 写入历史、丢弃工具消息**。它有两个后果：

- 好处：token 不随工具调用次数爆炸
- 代价：多轮时模型记不住"上一轮我查过什么"

三种策略的对比：

| 策略 | token 成本 | 失忆风险 | 实现复杂度 |
|---|---|---|---|
| 全量保留 | 随轮数线性增长，必然超限 | 无 | 最低 |
| 固定窗口 | 恒定 | **高**：被挤出的信息永久丢失 | 低 |
| **窗口 + 摘要** | 有上界 | 低：旧信息以压缩形式保留 | 中 |

选第三档。四个实现细节值得记下来：

1. **摘要只在超出窗口时触发，不是每轮**。每轮都摘要会让单轮成本翻倍。
2. **增量摘要**：压缩时把已有摘要一起交给模型合并，而不是丢掉重来。
   否则每次压缩都会丢失上一次保留的信息，摘要会越压越薄。
3. **摘要以 `system` 角色承载**。它在语义上是"背景设定"而非某一轮对话；
   用 `user`/`assistant` 的话，模型可能把它当成一条真实历史消息来回应。
4. **保留最近 `keep_recent` 轮原文**。摘要有损，越近的上下文越需要保真。

还有一个容易忽略的点：**没有 LLM 时要留下痕迹**。降级为截断是可以的，
但必须在摘要里写明"更早的对话已被丢弃" —— 静默丢弃上下文会让模型
表现异常却无从解释，排查时根本想不到是记忆模块干的。

## 三、长期记忆：几个必要的工程约束

- **去重**：Agent 可能反复被告知同一件事（"我在北京"）。重复存储会挤占召回
  名额，让真正有用的记忆排不进来。用文本归一化后精确比对，简单但够用。
- **写入必须写成自足的陈述句**。这条记录将来会脱离当前对话被单独召回 ——
  『只考虑北京』这样的片段在几天后读起来毫无意义，应写成
  『用户的求职意向城市是北京』。工具描述里明确要求了这一点。
- **索引失效**：新增事实后必须让向量索引失效，否则新记忆检索不到。
- **损坏文件不导致启动失败**：从空开始并记日志。记忆是增强项，
  它不该有能力阻止服务启动。
- **容量淘汰**：当前是"淘汰最早的"。生产环境应改为按访问时间淘汰，
  或让模型判断重要性 —— 前者需要记录访问，后者需要额外调用。
  当前实现是明确的技术债，不是没想到。

**已知局限（已用测试固定）**：TF-IDF 无法做同义/跨语言匹配。
查询『消息队列』找不到事实里的『Kafka』—— 不是"找不到"，而是"找得不准"，
相似度为 0 时排序退化为任意顺序。与 RAG 部分的结论一致：
**语义能力是当前系统的瓶颈**。

## 四、缺陷一：窗口内的轮次被静默丢弃（单元测试发现）

```python
# 初版
for turn in self._turns[-self.keep_recent:]:
```

`max_turns=5, keep_recent=3` 时，放进第 4 轮就会丢掉第 1 轮 ——
**而且没有摘要补偿**（因为还没触发压缩）。

信息凭空消失、不报错、不崩溃，只是模型偶尔"不记得"。
这正是记忆模块最该避免的失败模式，而它藏在两行代码的一个切片里。

**修正**：把职责分开 ——
`_maybe_compress` 负责裁剪并在裁剪时生成摘要，`abuild_context` 只负责
把**剩下的全部**轮次渲染出来。这样"什么时候丢"只有一处决策点。

## 五、缺陷二：同步实现的工具在真实路径上必然失败（端到端发现）

这是这一轮最有价值的教训。

`Tool` 基类把 `run` 声明为 `async def`，但 `RememberFactTool` 我写成了同步的
`def run(...)` —— 因为它的逻辑只是写个文件、查个内存表，写 `async` 看起来多余。

于是 `await self.run(params)` 抛出：

```
TypeError: object ToolResult can't be used in 'await' expression
```

**而单元测试全部通过**，因为测试里是直接调用 `tool.run(...)` 的。

两个关键点：

1. **副作用其实执行了**。同步体跑完了才轮到 `await` 报错，
   所以模型看到"失败"就重试，副作用被执行了两遍。
   这个 bug 不是"功能不可用"，而是"功能可用但会重复执行" —— 后者更危险。
2. **只有走 `Tool.execute` 的真实路径才暴露**。这正是"单元测试全绿不能替代
   端到端验证"的具体例子：单元测试验证了**函数的行为**，
   但没有验证**框架调用它的方式**。

**修正**：把同步/异步分派统一收进基类的 `Tool._invoke`：

```python
if inspect.iscoroutinefunction(self.run):
    return await self.run(params)
return await asyncio.to_thread(self.run, params)
```

这同时解决了第二个隐患：同步实现若直接在事件循环线程执行会阻塞整个进程，
而 `asyncio.wait_for` 拦不住不含 `await` 的同步代码。放进线程池后，
超时也才真正生效。

**并补了 4 个回归测试**：同步实现能跑通 `execute`、不阻塞事件循环
（用心跳计数验证）、超时生效、异常降级为观察结果。

## 六、端到端验证（跨进程）

```
第 1 轮  Agent 自主调用 remember_fact
         {"fact": "用户的求职意向：只考虑北京的工作岗位，期望月薪 30K 以上。",
          "tags": ["求职意向"]}
         ✓ 已记住（当前长期记忆共 1 条）

落盘      data/memory/facts.json 共 1 条（该目录被 gitignore 排除）

第 2 轮  新进程启动 → 记忆模块已启用，长期记忆已加载 1 条
         推荐岗位时使用了"只考虑北京"这条偏好（search_jobs city=北京）
         并主动提示："你的求职意向（城市北京、月薪 30K+）是我之前记下的，
         如果现在有变化请告诉我。"
```

最后那句确认话术是提示词要求的 —— **让用户可以纠正记错的内容**。
记忆系统不可信的时候，用户必须能发现并纠正它。

## 七、为什么记忆默认关闭

`MEMORY_ENABLED=false`。这不是保守，而是与检索消融实验**同一套方法论**：

> 一个功能的价值应该被度量，而不是被假设。

记忆会增加每轮的记忆装配与召回开销。在证明它带来净收益之前默认关闭，
需要的人显式开启（`--memory` 或环境变量）。

**下一步该做的度量**：构造多轮对话评测集，对比"有记忆/无记忆"下的
**任务完成率**与**用户重复信息次数**。单轮指标（如 Recall）测不出记忆的价值，
它需要的是多轮任务的成功率 —— 这也是 P4 评测体系要覆盖的部分。
