# STAR 故事（6 个，覆盖四类面试官最爱问的方向）

## 2026-10-06 新案例：三种编排共用工具，但没有真正共用预算

**S**：项目已经有大量通过测试，仍复现 Plan 配置丢失、整轮超时绕过、取消遗留专家、
Supervisor token 上限失效四个反例。

**T**：保持通用定位和既有接口，让规划、专家、工具与汇总受同一轮约束，并能证明中止后没有后续调用。

**A**：引入每轮独立 RunContext，子任务复制完整设置；模型边界记账，缺用量显式标记。
取消时关闭每层生成器并等待专家；将副作用互斥放在共享注册表。
为延迟、失败、预算隔离和真实 ASGI 断连写反例，保留只读并发对照；扩展 Edge 冒烟。

**R**：当前模型上三种正常任务、预算/超时与实际专家取消均已验证，累计 26 次受限请求尝试，
取消后没有遗留专家。界面冒烟还抓到悬挂 reader.read 无法停止的问题，修复后通过。
小样本结果、未知用量与未做生产标定均如实记录，见 [证据](../05-reliability-evidence.md)。

以下为历史案例；其中的测试数、阶段名称与部署指标保留历史条件，不作为本轮复测结果。

> 用法：**每个故事讲 90 秒**。S/T 各 15 秒铺背景，A 占 45 秒（这部分是你真正做的），R 用 15 秒给数字。
> 讲砸的常见方式是 A 太短、S 太长 —— 面试官不关心背景有多复杂，只关心**你怎么想的**。
>
> 六个故事按"踩坑并解决 / 设计取舍 / 性能优化 / 质量保障"四类分布，
> 每个都带**真实的错误信息或测量数字** —— 这些细节是故事可信度的全部来源。

## 故事 1【踩坑并解决】pip 把包装到了 Python 3.9，虚拟环境形同虚设

**S｜背景**
项目起步，建好 `.venv`（Python 3.12.3）后装依赖，一切正常。但换了一台机器复现时，
`pytest` 报 `ModuleNotFoundError`，而 `pip list` 里明明有。

**T｜任务**
为什么虚拟环境里装了包，运行时却找不到？

**A｜行动**
查了三层：
1. `pip -V` 显示的安装路径不是 `.venv`，而是 `E:\Python\Python39\Lib\site-packages` —— 一个已经 EOL 的系统 Python。
2. 找原因：环境里有一个**用户级** `PIP_TARGET` 变量，它会让 pip 无视当前虚拟环境、强制装到指定目录。
3. 想根治：改全局配置删掉它。

**这一步我停了。** 那台机器上可能有别的东西依赖这个变量，我不该为了让自己项目跑起来去改别人的全局环境。
改成在项目脚本里每次清掉：`Remove-Item Env:PIP_TARGET`，并在 `scripts/dev.ps1` 里固化。

同一轮还发现第二个坑：pip 默认缓存目录被文件沙箱拒绝，导致下载**卡住 7 分钟**（CPU 空转而不是报错）。
把 `PIP_CACHE_DIR` 指到工作区内的 `.pip-cache/` 后降到 **4.5 秒**。

**R｜结果**
装依赖从"卡住 7 分钟 + 装错地方"变成 4.5 秒且必装在虚拟环境内；
这两个坑都写进了 `scripts/dev.ps1` 的头部注释和文档里，**换机器不会再踩**。

**这个故事的真正考点**：分辨"该修环境"和"该让代码适应环境"。
用户级配置不是我的资产，动它有风险；但也不能假装它不存在 —— 正确做法是**在项目边界内消化掉它**。

## 故事 2【踩坑并解决】PowerShell 报错指向一行无辜的中文注释

**S｜背景**
给 `scripts/dev.ps1` 加了几个子命令（启动 RAG 服务、独立 worker 等）之后，
脚本突然完全无法运行。PowerShell 报：

```
At scripts\dev.ps1:50 char:22
+  Write-Host "[x] 找不到虚拟环境：$VenvPython" -ForegroundColor Red
Array index expression is missing or not valid.
```

**T｜任务**
第 50 行是什么？—— **一句中文注释** `# 只处理当前进程的环境变量设置，不改动用户级全局配置。`

报错行号和真实问题完全没有关系，这是最消耗时间的一类 bug。

**A｜行动**
1. 先用 `Parser::ParseFile` 对比 **git 里的 HEAD 版本和当前版本**：HEAD 解析 0 错误，当前 2 错误 —— 确认是我改坏的。
2. 但报错位置对不上，说明**解析器看到的文本和我读到的不是同一份**。
3. 查 `$PSVersionTable`：`5.1`。而 PowerShell 5.1 **只在见到 UTF-8 BOM 时才按 UTF-8 解码 `.ps1`**，否则按系统 ANSI 代码页 —— 这台机器是 GBK。
4. 根因：中文在 UTF-8 里是 3 字节；GBK 把前两字节当成一个汉字，剩下的第三字节（`0x80-0xBF`）单独成字 ——
   而它在 GBK 里是**合法的首字节**，于是**继续吞掉后面那个字节**（常常是换行或引号）。
   字节配对整体位移，语法树就崩了，而行号也跟着错位。

**最关键的一点**：HEAD 版本**只是碰巧字节对齐没出事**。我加了几行中文注释，配对整体偏移，就炸了。
也就是说这个脚本一直是脆的，只是没暴露。

**R｜结果**
给所有 `.ps1` 补上 UTF-8 BOM，解析 0 错误。
并且做了两件防止复发的事：
- 写 `scripts/fix_ps1_bom.py`，接进 `dev.ps1 check` 的**最前面**变成自愈步骤 —— 因为任何编辑工具都可能顺手去掉 BOM（本项目的 edit 工具就会，实测又触发了一次）。
- 加 `TestPowerShellEncoding` 回归门禁，缺 BOM 直接 CI 失败。

**这个故事的真正考点**：**"这个错误信息在说别的事情"** 是一种必须尽早意识到的信号。
以及：报告 0 错误≠文件没问题，可能是字节对齐的运气。

## 故事 3【设计取舍】为什么手写 Agent 内核而不用 LangChain

**S｜背景**
做 Agent 项目时，LangChain / LlamaIndex 已经能把 ReAct 循环、工具协议、记忆都封装好，
看起来"一上午就能跑起来"。

**T｜任务**
选框架还是自己写？

**A｜行动**
我先问了一个问题：**出问题的时候，我能定位到哪一层？**

Agent 的失败面比普通服务宽得多：模型可能答错、工具参数可能解析错、流式分片可能聚合错、
提示词可能让模型不用工具。用框架的话，这四种失败**看起来是一样的** —— 都是"回答不对"。
而自己写，这四件事分别在我的四个文件里。

于是决定手写。代价我也先列清楚了：
- 流式下 `tool_calls` 的分片聚合要自己处理（**按 `index` 聚合，不能按 `id`** —— 因为 id 本身也是分片来的）
- 工具错误要转成"观察结果"回灌给模型，而不是抛异常
- 死循环检测要自己做（用**参数指纹**而不是只看工具名）

**R｜结果**
产出三种 Agent 形态（ReAct / 规划型 / 多智能体主管-工人），**共用同一套工具与护栏层**。
这个"共用"是刻意的：两套实现迟早不一致，而那时你**分不清差异来自范式不同还是实现不同**。

**如果被追问"那框架的价值呢"** —— 诚实回答：
框架在**标准化**和**生态集成**上的价值是真的（几十种向量库、几十种加载器，自己写不现实）。
我的判断只适用于一件事：**当这个循环本身就是要学的东西时，自己写一遍的收益大于成本**。
如果是做产品交付，我会直接用框架，然后把省下的时间花在评测和业务上。

## 故事 4【设计取舍】熔断器：最容易写错的不是算法，是"什么算失败"

**S｜背景**
把 RAG 检索拆成独立服务之后，引入了一个单体模式**根本不存在**的失败模式：
RAG 挂掉时，agent 每次检索都要**等满 15 秒超时**。
后果不是"检索变慢"，而是 agent 自己被拖死 —— 待处理请求越堆越多，最后连不依赖检索的对话也一起不可用。

**T｜任务**
加熔断器。连续失败 5 次后直接快速失败，30 秒后放一个探测请求恢复。

**A｜行动**
状态机本身很简单。**但我在写测试的时候发现了一个更隐蔽的问题**：

`EmptyKnowledgeBase`（知识库为空）会返回 HTTP 503。这在熔断器的朴素实现里就是一个失败。
于是：一个刚部署、**语料还没准备好**的实例，前 5 次检索（每次都是正常返回 503）
就会把自己的熔断器打开，之后所有请求都报"知识库服务不可用"。

而服务**完全健康**，只是没有数据。运维会去查"服务为什么挂了"—— **排查方向从一开始就是错的**。

所以我给熔断器加了一个 `count_as_failure` 回调，显式把业务状态排除在故障之外。
连带还有第二个坑：业务状态**必须归还半开探测名额**，否则一次"知识库为空"就把唯一的名额永久占住，熔断器再也不会恢复。

**R｜结果**
- 熔断后 **20 次调用合计 < 50ms**（未熔断需 1.0s）—— 测试断言的是**真实耗时**而不是状态字段。
  原因是：一个有 bug 的实现完全可以把状态标成 `open` 然后继续傻等超时，状态断言照样通过，而熔断毫无作用。
- "业务状态不触发熔断"由专门的测试固定，并且是**走真实 HTTP**（ASGITransport）验证的。

**这个故事的真正考点**：**故障（fault）与业务状态（state）必须分开统计** ——
这个区分在单体模式下不存在，是分布式才暴露出来的。

## 故事 5【性能优化】用测量证明"该不该拆"，以及拆的顺序

**S｜背景**
单体跑得很好。要不要拆微服务？"架构上更优雅"不是一个理由。

**T｜任务**
先证明拆分**确实解决一个真实问题**，再决定拆什么、怎么拆。

**A｜行动**
**第一步：量化问题。** 我写了个压测脚本，故意在检索的同时持续触发索引重建
（两者都是纯 CPU 计算），对比同一接口的延迟分布：

| 场景 | QPS | P95 | P99 |
|---|---|---|---|
| 检索（正常） | 109.9 | 80.9ms | 86.8ms |
| 检索（重建索引进行中） | 73.0 | **124.3ms** | **169.0ms** |

**P95 放大 1.5×、P99 放大 1.95×** —— 这就是"该拆"的证据，不是形容词。

**第二步：决定拆的顺序。** 我刻意**没有**先搬代码。因为如果第一步就同时搬代码，
出问题时你无法判断是"拆分设计有问题"还是"搬运时漏了什么" —— 两个变量同时变，排障只能猜。

正确顺序是：**进程边界 → 接口边界 → 仓库边界**，做到第二步就够了。

**第三步：接口边界才是真难点。** 原来工具层依赖一个**隐式契约**：
`len(retriever.chunks) == 0` 表示知识库为空。它在同进程永远成立，**一跨网络就彻底失效** ——
远程调用方根本拿不到那个内存列表。

所以我先抽出显式接口（只有 2 个方法），让工具只依赖接口，**然后**才写远程实现。
做完前两步，第三步几乎是免费的。反过来（先写 HTTP 客户端再想接口）会得到一个又宽又别扭的接口。

**R｜结果**
拆成 `api` / `rag` / `worker` 三个进程角色，且保留一个环境变量切回单体（安全网）。
验证方式我也刻意加严了：不满足于"有结果返回"，而是去 **RAG 服务自己的指标端点**
确认请求计数真的涨了（实测 13 → 16）—— 因为**"有结果"不等于"请求真的到达了那个进程"**，
配置写错时 agent 会静默地在自己进程里另建一份索引，服务健康、回答正确，但拆分完全没生效。

**这个故事的真正考点**：拆分的第一步不是搬代码；以及**静默失效比报错危险得多**。

## 故事 6【质量保障】测试通过了，但功能是坏的

**S｜背景**
给 `scripts/dev.ps1` 加了几个子命令后，我加了一条测试：

```python
for cmd in ("rag", "worker", "serve-split"):
    assert f"'{cmd}'" in text   # 断言子命令名出现在文件里
```

测试通过。但实际执行 `.\scripts\dev.ps1 rag` 时，PowerShell 直接拒绝：
**参数不在集合中**。

**T｜任务**
为什么测试通过了，功能却完全不可用？

**A｜行动**
原因：PowerShell 的 `ValidateSet` 是**参数绑定阶段**执行的，不在名单里的值会在进入 `switch` 之前就被拒绝。
我加了 `switch` 分支、更新了注释，但**忘了改 `ValidateSet`**。

而我的断言只检查了"字符串 `'rag'` 出现在文件中"—— 这个字符串出现在
**注释里、`switch` 里、`ValidateSet` 里**都算通过。三种情况的行为却完全不同：
- 在注释里 → 完全没有这个功能
- 在 `switch` 里但不在 `ValidateSet` → 调用被拒绝（就是这次）
- 两处都有 → 正常工作

**我断言的不是"功能生效的结构"，而是一个几乎处处成立的弱条件。**

**R｜结果**
改成断言真正的不变量：**`switch` 里的每个标签都必须在 `ValidateSet` 里**，
并且反过来检查 `ValidateSet` 里没有多余项（那些会静默走到 `default` 打印帮助，看起来像"命令没生效"）。
用正则解析两个集合做集合差，任何一边不匹配就失败。

同一个思路后来抓到了第二个问题：编辑 `.ps1` 会去掉 BOM（故事 2 的根治手段），
而**刚加的 BOM 门禁测试立刻报错** —— 这验证了那条门禁是真的有用，不是摆设。

**这个故事的真正考点**：**"断言某个符号存在"几乎不构成验证**。
这是写测试时最容易掉进去的陷阱，而且它比不写测试更糟 —— 因为它给了你虚假的安全感。

**被追问"你最大的不足是什么"时的诚实答法**（比编一个假缺点好得多）：

> 我的检索评测集只有 14 条查询，样本量小、指标波动大。

> 那部分才真正检验"会不会编造"。
