## 一、大模型基础与推理（#1–#4）

### #1 KV Cache 原理与显存估算 🟡
**问法**：7B 模型 32K 上下文，KV Cache 单条要多少显存？怎么反推并发数？

**答**：KV Cache 缓存的是每一层注意力里已经算过的 K 和 V 矩阵，避免 decode 阶段每生成一个 token
就把整个前缀重算一遍。容量是
`2（K和V）× 层数 × 头数 × 头维度 × 序列长度 × 精度字节数`。
以 7B（32 层、32 头、头维度 128）为例，单 token 的 KV 约 `2×32×32×128×2字节 ≈ 512KB`（fp16），
32K 上下文就是 **约 16GB** —— 已经超过模型权重本身。

所以并发数的反推不是"显存除以权重"，而是 **显存减去权重后除以 KV Cache 的单条占用**。

**落点**：`docs/02-concepts/01-llm-basics.md`
**诚实边界**：这是纸面计算，我没在真实 GPU 上验证过。真实环境还要考虑碎片、CUDA context、激活值。

### #2 Prefill vs Decode 的物理差异 🟡
**问法**：为什么 decode 是 memory-bound 而不是 compute-bound？

**答**：Prefill 一次处理整个提示词，矩阵乘的算术强度高，**吃算力**；
Decode 每次只生成一个 token，却要把**全部权重和全部 KV Cache 从显存读进计算单元** ——
计算量极小、访存量极大，所以**吃带宽**。

这解释了推理优化的整个方向：Continuous Batching 是为了在 decode 阶段凑批、把访存摊薄；
PagedAttention 是为了解决 KV Cache 的显存碎片；投机解码是让小模型先猜、大模型批量验证，
**把多次低效的 decode 变成一次高效的 verify**。

**落点**：`docs/02-concepts/01-llm-basics.md`
**诚实边界**：没做过本地部署调优。

### #3 采样参数 🟢
**问法**：工具调用场景为什么把 temperature 压到 0.3 以下？top_p 和 temperature 同时调会怎样？

**答**：工具调用要求的是**结构化输出的可靠性**，不是创造性。temperature 越高，
JSON 结构出错、参数名编造的几率越大。所以本项目的默认值是 **0.3**。

`temperature` 和 `top_p` **不应该同时调**：前者是缩放整个 logits 分布（改变形状），
后者是按累积概率截断候选集（改变范围）。两者叠加的效果难以预测，
**调一个、固定另一个**才是可控的。

**落点**：`services/api/app/core/config.py`（`LLM_TEMPERATURE=0.3`）、`.env.example`
**可以展开**：更关键的不是采样参数，而是**容错**——模型输出了非法 JSON 怎么办。
本项目的做法是**不抛异常**，而是带上错误信息把 Schema 回灌给模型让它自修（见 #7）。

### #4 推理优化（PagedAttention / Continuous Batching / 量化 / 投机解码）🟡
**答**：见 #2 的分析链。补充一个面试常被追问的区分：
**Continuous Batching 提升的是吞吐，不是单请求延迟** —— 它让不同请求在不同时间进出同一个批次，
把 GPU 利用率从"等最慢的那个"里解放出来。但它会让单个请求的完成时间变得更不可预测。
**落点**：`docs/02-concepts/01-llm-basics.md`

## 二、Agent 与工具调用（#5–#15）——**这一组是可以主动引导的主场**

### #5 tool_calls 协议细节 🟢
**问法**：模型返回的 `arguments` 为什么是字符串？`role=tool` 消息不带 `tool_call_id` 会怎样？

**答**：`arguments` 是**字符串**（不是对象）是刻意的：模型是逐 token 生成的，
JSON 是"生成出来的文本"，协议上就保持文本形态，由客户端负责解析。
这也意味着**解析失败是常态而非异常** —— 必须容错。

`tool_call_id` 是**配对钥匙**：一次可能并发调用多个工具，`role=tool` 消息靠 id 与
对应的 `tool_calls` 条目配对。不带 id（或 id 对不上）时，大多数 API 直接 400；
即使不报错，模型也无法知道哪个结果属于哪个调用 —— 表现为"模型把两个工具的结果串在一起用"。

**落点**：`services/api/app/llm/types.py`（协议类型）、`services/api/app/agent/loop.py`（回灌构造）
**项目里的实证**：`ToolCall` 保留了 `raw_arguments` 字段，当 JSON 解析失败时用它兜底 ——
**因为"解析失败"本身是要告知模型的信息**，丢掉原始文本就没法让它自修。

### #6 流式响应的 tool_calls 分片重组 🟢
**问法**：流式下 `tool_calls` 的分片按什么键聚合？为什么不能按 id？usage 在哪个 chunk？

**答**：**按 `index` 聚合，不能按 `id`** —— 因为 `id` 本身也是分片来的，
第一个分片里可能只有 `index` 和部分 `id`，用 `id` 做键会把同一次调用拆成多个。
`arguments` 更是逐字符分片到达的，必须字符串拼接。

`usage` 在**最后一个 chunk**（且流式下必须显式传 `stream_options: {include_usage: true}`，
否则整个流里一个 token 数据都拿不到 —— **这是最容易漏的协议细节**）。

**落点**：`services/api/app/llm/client.py`（`StreamAccumulator.feed`）、
`services/api/app/llm/client.py:149-150`（`include_usage`）
**项目里的实证**：`tests/test_stream.py` 用真实分片样本驱动聚合逻辑，
其中有一组就是"按 id 聚合会失败"的对照。

### #7 结构化输出的可靠性 🟢
**问法**：模型输出非法 JSON 你怎么办？为什么不重试而要把错误回灌给模型？

**答**：**重试是盲目的** —— 再问一次同样的提示词，模型很可能犯同样的错，
而且每次重试都要付一次完整的 prompt token 成本。

回灌不一样：把**具体的校验错误**（哪个字段缺失、类型不对）加上 Schema 一起作为观察结果回灌，
模型拿到的是**新信息**，它能针对性地修。这是 Agent 相对"一次调用"的本质区别：
**错误成为下一轮的输入**。

**落点**：`services/api/app/tools/base.py`（校验失败回灌 Schema）、
`services/api/app/llm/types.py`（解析失败不抛异常）、
`services/api/app/llm/client.py`（`response_format` 400 自动降级）

### #8 Pydantic → JSON Schema 的工具建模 🟢
**问法**：工具参数模型改一个字段，模型看到的东西会变吗？描述写得含糊会有什么后果？

**答**：会。`model_json_schema()` 直接把字段名、类型、约束、`description` 变成模型看到的工具定义。
所以**改 Pydantic 模型等于改模型的 API 文档**。

描述含糊是 Agent 表现差的**第一大原因，比换模型有效得多**。本项目在工具描述里写四件事：
1. 什么时候该用（触发条件）
2. **什么时候不该用**（避免滥用 —— 比如明确写"精确算术请用 calculator"）
3. 参数含义与边界
4. 返回什么

**落点**：`services/api/app/tools/base.py`、`services/api/app/tools/knowledge.py`（描述写法）
**可以展开**：`tests/test_knowledge_tool.py` 里有一条测试专门断言描述里
**包含"不该用"的指引**（必须提到 `calculator` 和 `search_jobs`）—— 描述质量也是可测的。

### #9 Agent 错误自愈（错误即观察结果）🟢
**问法**：工具报错为什么不抛异常？把错误吞掉伪装成空结果会怎样？

**答**：**这两种做法都错，而且错在不同方向**：

- **抛异常**：整个 Agent 循环中断。但工具失败（参数填错、临时网络问题）是**可恢复**的，
  模型看到错误信息完全可能换个参数重试 —— 抛异常把这个机会扔掉了。
- **吞掉伪装成空结果**：更危险。模型看到"空结果"会推断"**这个东西不存在**"，
  进而给出错误结论（比如"你没有相关经验"），而真相是"检索服务当时挂了"。
  **这是最隐蔽的一类错误：它把一个故障伪装成了一个事实。**

正确做法：把错误**结构化地**作为观察结果回灌，并且**保留错误的语义分类**
（是参数问题、超时问题、还是服务不可用），让模型能针对不同类别做不同处理。

**落点**：`services/api/app/tools/errors.py`（语义分类）、`services/api/app/tools/base.py`、
`services/api/app/agent/loop.py`
**项目里的实证**：工具层对"熔断"和"下游故障"给出**不同的**提示 ——
熔断时明确告诉模型"**不要重试**"（我们根本没发起调用，重试必然失败），
故障时才建议换个方式再试。如果把两者混为一谈，模型会去重试 ——
而重试恰好是熔断器最想阻止的行为。

### #10 ReAct 范式与终止条件 🟢
**问法**：ReAct 循环什么时候停？`finish_reason=tool_calls` 和"消息里有 tool_calls"哪个判据更稳？

**答**：**"消息里有 tool_calls" 更稳**。`finish_reason` 是各家 API 的约定，
不同厂商、不同模型版本可能不一致（有的返回 `tool_calls`，有的返回 `stop` 但消息里带工具调用）。
而"assistant 消息里有没有 tool_calls"是**消息结构本身的事实**，不依赖厂商约定。

**落点**：`services/api/app/agent/loop.py`
**可以展开**：这个判断有个真实后果 —— 用 `finish_reason` 判的话，
某次 API 变更会导致工具调用被当成"最终回答"直接返回给用户，
表现为"Agent 把工具名当答案回复了"，而且不报错。

### #11 Agent 成本护栏（步数预算 + 死循环检测）🟢
**问法**：没有 max_steps 的 Agent 在生产会发生什么？死循环检测为什么用参数指纹而不是只看工具名？

**答**：没有 `max_steps`，一个把工具当"思考"用的模型会**无限调用**，
每一步都把之前的完整上下文再发一次 —— 成本随步数**近似平方增长**（每一步的 prompt 都更长）。
这不是"多花点钱"，而是单个请求就能烧掉一个月的额度。

**用参数指纹而不是只看工具名**：Agent 卡住的典型形态是
"调同一个工具、传同样的参数、拿同样的结果、再调一次"。
只看工具名会把"连续三次调 `search_knowledge` 但查询词不同"误判成死循环 ——
而那完全可能是正常的（先查简历、再查岗位、再查笔记）。
用 `SHA1(工具名 + 参数)` 做指纹，**只有参数完全相同才判定为循环**。

**落点**：`services/api/app/agent/loop.py`（`_call_signature` 用 SHA1）、`config.py`（`loop_guard=3`）
**项目里的实证**：判定为循环时不抛异常，而是**终止并返回已有结果**，同时在事件流里标明
`stopped_reason` —— 用户能看到"它卡住了"，而不是等一个永远不会来的回答。

### #12 Prompt 工程 🟢
**答**：`SYSTEM_PROMPT` 单独成模块（`agent/prompts.py`），内容分四块：
能力边界、工具使用规则、诚实性要求（不知道就说不知道）、输出风格。

**问法里那个问题（工具描述 vs 系统提示词哪个影响更大）**：
**工具描述影响更大**，而且更可控。因为工具描述是**模型在决策那一刻直接读到的 API 文档**，
系统提示词是全局背景。经验上：改一句工具描述的 `description`，
对调用准确率的影响往往大于调整系统提示词。

## 三、工程基础（#13–#15）

### #13 SSE 服务端实现与心跳 🟢
**问法**：SSE 和 WebSocket 怎么选？长连接被反向代理掐断怎么办？为什么用 POST？

**答**：**SSE 是单向的（服务端→客户端）**，而 Agent 的流式回答正好是单向的 ——
用 WebSocket 会引入双向通道、心跳协商、连接状态机这些**不需要的复杂度**。
选 SSE 是"选够用的那个"。

**心跳**：中间层（nginx、云负载均衡）会掐掉长时间无数据的连接。
`sse_starlette` 的 `ping` 参数定期发注释行保活，本项目设 15 秒。

**用 POST 而不是 GET**：消息内容放请求体更自然、不受 URL 长度限制、也不该出现在访问日志里。
代价是前端**不能用 `EventSource`**（它只支持 GET），必须用 `fetch` + `ReadableStream` 手动解析 ——
本项目前端就是这么做的（`src/lib/sse.ts` 是手写的分帧器）。

**落点**：`services/api/app/api/routes.py`、`services/api/app/agent/events.py`

### #14 异步 I/O、超时与取消传播 🟢
**问法**：在 async 函数里直接调 `input()` 会怎样？`CancelledError` 为什么必须透传？

**答**：`input()` 是**阻塞调用**，会卡住整个事件循环 —— 不是卡住这一个请求，是卡住**所有**请求。
在 CLI 里表现为"Agent 在等输入时，另一个并发请求也不动了"。
正确做法是 `await asyncio.to_thread(input)`，把阻塞调用丢到线程池。

**`CancelledError` 必须透传**：从 Python 3.8 起它继承 `BaseException` 而不是 `Exception`，
就是为了防止被 `except Exception` 吞掉。超时（`wait_for`）的实现就是"取消任务"，
如果工具层把取消当成普通异常吞掉，**超时机制就静默失效了** ——
表现为"设了 60 秒超时，但请求跑了 10 分钟"。

**落点**：`services/api/app/tools/base.py`（`wait_for` + `CancelledError` 显式透传）、`services/api/cli.py`

### #15 可重试 vs 不可重试的错误分类与退避 🟢
**问法**：429 和 401 该重试哪个？退避为什么必须加抖动？重试和超时怎么配合？

**答**：**只重试 429、5xx、网络超时**；**401/403/400 绝不重试** ——
401 是密钥错，重试一万次还是错，只是把错误延迟暴露并浪费时间。

**抖动（jitter）是必需的**：纯指数退避下，一批同时失败的请求会在**同一时刻**一起重试，
形成周期性的尖峰 —— 这就是"重试风暴"，它会把正在恢复的服务再打一次。
加随机抖动把重试时刻打散。

**重试与超时必须联合设计**：`最大重试次数 × 单次超时 + 退避总时长` 必须小于上游的请求超时，
否则重试还没做完，上游已经放弃了 —— 那些重试变成纯粹的浪费。

**落点**：`services/api/app/llm/client.py`（异常体系分层 + 退避带抖动）

## 四、记忆、RAG、缓存、任务队列（#16–#25）——**P2/P3 落地后已全部变绿**

### #16 短期记忆：滑动窗口 + 摘要压缩 🟢
**问法**：单纯截断最早的消息有什么问题？摘要丢的是什么信息？怎么判断该摘要了？

**答**：**单纯截断的问题是"突然失忆"**。用户在第 3 轮说过"我要找北京的岗位"，
第 9 轮被截掉之后，模型会开始推荐上海的岗位，而且**没有任何提示** ——
用户只会觉得"这 AI 有点傻"。

摘要是有损的，丢的主要是：**具体数字、专有名词、否定信息**（"我不要远程岗位"）。
所以本项目的策略是"**超出窗口时压缩旧轮次，但保留最近 N 轮原文**" ——
越近的上下文越需要保真。`MEMORY_KEEP_RECENT` 不能设太小。

**怎么判断该摘要**：本项目按**轮数**而不是 token 数触发（简单可预测），
超出 `max_turns` 才压缩一次，所以是"每超出一次多一次 LLM 调用"，不是每轮都调。

**落点**：`services/api/app/agent/memory.py`（`ConversationMemory.abuild_context`）
**诚实补充**：记忆功能**默认关闭**（`MEMORY_ENABLED=false`）——
因为它会增加每轮的记忆装配与召回开销，**它的价值应该被度量而不是被假设**。
这跟检索消融实验是同一套方法论。

### #17 上下文窗口与 token 预算 🟢
**答**：项目现状是按**字符数**控制（工具输出 8000 字符、RAG 上下文 3000 字符）。
**这是一个已知的近似**：中文大约 1 字符 ≈ 0.6~1 token，但这个比例随内容变化很大
（代码、英文、数字的比例不同，token 密度差好几倍）。

所以"按字符控制"能挡住最坏情况，但**做不到精确的成本预算**。
要精确需要引入 tokenizer（`tiktoken` 或模型自带的计数器），
并且要在**每一次工具结果回来之后**重新计算，而不是只在入口算一次。

**诚实边界**：没做精确 token 预算。面试时应当主动说这是近似，并说明精确做法。

### #18 Embedding 选型、归一化与相似度度量 🟢
**问法**：归一化后内积和余弦等价吗？维度砍半损失什么？

**答**：**归一化之后等价**。余弦相似度 = `(a·b)/(|a||b|)`，
若 `|a|=|b|=1` 则分母为 1，余弦退化成内积。所以工程上常把向量归一化后只用内积 ——
省掉每次计算时的模长运算。

**本项目用的是 TF-IDF 而不是神经 embedding**，这是一个**刻意的选择**：
零依赖、可解释、在几十块的语料上够用，而且**不会引入一个需要下载模型权重的启动依赖**。
代价是它**没有语义泛化能力** —— 查"联系方式"命不中"邮箱"（本项目评测里确实有这条失败案例）。

**落点**：`services/api/app/rag/embedder.py`；抽象接口已留出（`EmbeddingBackend`），换神经 embedding 不影响上层。
**可以展开**：那条失败案例我保留了没删 —— 它精确地说明了"词法检索的边界在哪"。

### #19 向量索引：HNSW 与 IVF 🟡
**答**：`M` 控制每个节点的连接数（越大召回越高、内存越多）；
`ef_search` 是查询时的候选队列长度（越大越准越慢）。**这是"召回换内存/延迟"的旋钮**。
IVF 是聚类+倒排，**内存更省但需要训练**，适合超大规模；
HNSW 是图索引，**查询更快更准但内存占用高**。

**诚实边界**：🔴 本项目**没有用**任何近似索引 —— 语料只有几十块，
numpy 暴力算全量余弦**就是最优解**（没有近似误差，而且足够快）。
面试时应该说"我读过原理，项目里因为数据量小用的是暴力检索"，
**而不是暗示自己调过 HNSW 参数**。

### #20 混合检索与 RRF 融合 🟢
**问法**：为什么招聘语料要混合检索？RRF 的 k 值语义是什么？为什么比加权求和更省调参？

**答**：招聘语料的特点是**大量专有名词**（Kafka、Flink、ClickHouse、RAG）。
稠密检索（TF-IDF/embedding）擅长语义但会漏掉精确术语；
BM25 擅长精确匹配但不懂同义改写。**两者的失败模式不重叠，所以融合有收益** ——
实测混合 RRF 把 Recall@5 从 0.821 提到 **0.869**。

**RRF 的 k 值**（本项目 60）是平滑常数：`score = Σ 1/(k + rank)`。
它决定了"排名靠前的差异有多重要" —— k 越小，第 1 名与第 2 名的分数差越大。

**为什么比加权求和省调参**：余弦相似度在 0~1，BM25 是无上界的正数，
**量纲完全不同，加权求和在工程上不可靠**（换个语料 BM25 的量级就变了，权重全废）。
RRF 融合的是**排名**而不是分数，天然免疫量纲问题 ——
**只需要一个 k，不需要标定两个权重**。

**落点**：`services/api/app/rag/fusion.py`

### #21 Rerank 与阈值拒答 🟢
**问法**：召回 30 条 rerank 到 5 条，延迟增加多少？为什么求职场景"拒答"比"编一个答案"更好？

**答**：本项目实测（单机本地）**RAG `/context` 端到端 P95 80.9ms**，
其中重排（词法重排）的增量在个位数毫秒量级 —— 因为是查表式的词法打分，
不是 cross-encoder 的模型推理。

**LLM 重排**效果显著更好（MRR +0.414）但**每次查询多一次 LLM 调用（约 2361 tokens）**，
在 Agent 循环里会成倍放大，所以**默认关闭**。这是一个"效果好但成本不可接受"的典型取舍。

**为什么拒答更好**：求职场景下，用户会**依据这个结论做决策**（投不投这个岗位）。
编造一个"你有相关经验"的回答，用户可能因此去投一个完全够不上的岗位，
或者基于虚假经历准备面试 —— **代价远大于"没找到"**。
所以本项目在检索不到时明确回答"资料里没有相关内容"，并给出下一步建议（换表述、扩大 scope）。

**落点**：`services/api/app/rag/rerank.py`、`services/api/app/rag/retriever.py`（相关性闸门）、
`services/api/app/tools/knowledge.py`（拒答提示）
**可以展开**：闸门**默认关闭**（`RAG_MIN_SCORE=0.0`）。
因为 RRF 只提供相对排名、"永远凑满 k 条"的问题真实存在，但**合理阈值高度依赖语料**，
设错会静默丢掉正确结果。所以默认关闭 + 文档说明"要开启请先在评测集上标定"。

### #22 RAG 评测指标与消融实验 🟢
**问法**：Recall@k 和 MRR 衡量什么？怎么搭最小评测集？为什么必须包含"不可回答"样本？

**答**：**Recall@k** 衡量"正确答案有没有进前 k 条"（召回能力）；
**MRR** 衡量"第一条正确答案排在第几位"（排序质量）。
两者要分开看，因为它们指向不同的优化动作：
- Recall 高、MRR 低 → 答案在候选里但排序差 → **该做重排**
- Recall 本身就低 → **召回层问题，重排救不回来** → 该查切分与查询改写

本项目把这句话直接写进了评测报告的"读表提示"里。

**为什么必须有不可回答样本**：只测"能答对的"会得到一个漂亮但无意义的分数 ——
检索系统永远会返回 k 条，**测不出它会不会硬编**。
只有放进"语料里根本没有答案"的问题，才能测出拒答能力。
这类样本应该占评测集的 **≥20%**。

**落点**：`services/api/app/rag/evaluate.py`、`scripts/eval_rag.py`、`services/api/seed/eval_set.json`
**项目里的实证**：消融表（`--compare`）在这个评测集上跑出 5 条管线的对比，
其中 **"混合+重排反而不如纯混合的召回"** 这个负结果我也保留了 ——
它说明重排在 top-k 截断时会丢召回了部分召回，据此把重排定位为**排序优化而非召回优化**。

**诚实边界**：评测集只有 14 条查询，**样本量小**。用它做回归门禁合适，
当"检索能力有多强"的结论是过度解读。

### #23 缓存穿透 / 击穿 / 雪崩与 TTL 🟢
**答**：三者的区别在于**缓存为什么没挡住这次请求**：

| | 原因 | 解法 |
|---|---|---|
| **穿透** | 查的数据**根本不存在**，每次都打到 DB | 缓存空值（短 TTL）+ 布隆过滤器 |
| **击穿** | **某个热点 key 过期**的瞬间，大量请求同时打到 DB | 互斥锁/单飞（single-flight）：只放一个请求去重建 |
| **雪崩** | **大量 key 同时过期**，或缓存整体挂掉 | TTL 加随机抖动（避免同时过期）+ 多级缓存 + 熔断降级 |

**TTL 设计的关键是加抖动**：如果一批 key 在同一秒写入，同一秒过期，
那它们在过期那一刻会同时打 DB —— 这就是雪崩的成因。加 ±10% 的随机偏移就能打散。

**落点**：本项目在会话层用了 Redis（`session/store.py`），
**诚实边界**：🔴 **本项目没有实现"穿透/击穿/雪崩"的具体防护** ——
因为是单用户作品集项目，没有热点竞争。
面试时应该讲原理 + 说明"AIVideo 里用了 Cache Aside"（那是真实经验），
**不要暗示 JobPilot 做过这些**。

### #24 Redis 数据结构选型 🟢
**答**：按访问模式选，不是"一把 String 存 JSON"：

- **会话历史**：要整体读写、不需要部分更新 → **String（序列化 JSON）**。本项目就是这么做的。
- **限流计数**：要原子自增 + 过期 → **String + `INCR` + `EXPIRE`**，
  或者用 **ZSet** 做滑动窗口（score 存时间戳，`ZREMRANGEBYSCORE` 清理旧记录）。
- **排行榜/优先级队列**：要按分数排序 → **ZSet**。
- **任务队列**：要阻塞弹出 → **List（`BRPOP`）** 或 **Stream**。
- **对象的部分字段更新**（比如"只改会话的最后活跃时间"）→ **Hash**。

**为什么不用一把 String 全塞 JSON**：**并发更新会互相覆盖** ——
两个请求同时读-改-写同一个 JSON，后写的会丢掉先写的字段。
Hash 可以只更新单个字段，Redis 的单命令是原子的。

**落点**：`services/api/app/session/store.py`（String 存会话）、
`services/api/app/tasks/redis_queue.py`（List + BRPOP）

### #25 消息队列：至少一次、幂等、死信 🟢（但**有一个必须主动说的缺口**）
**问法**：重复消费怎么保证幂等？失败重试几次后去哪？顺序性怎么保证？

**答**：**幂等键**通常是"业务唯一标识 + 内容 hash"：
处理前先查这个键有没有处理过（Redis SETNX 或数据库唯一索引），
处理过就直接返回成功 —— **让重复投递变成无害操作**。

**死信队列**：重试 N 次（通常带指数退避）仍失败的消息转入 DLQ，
**不再自动重试但保留下来供人工排查**。关键是**必须有上限** ——
无限重试会让一条毒消息永久占用消费者。

**顺序性**：Kafka 靠**分区内有序**（同 key 进同分区）；
Redis List 天然是 FIFO 但如果多个消费者就**不保证**了。

⚠️ **本项目必须主动说的缺口**：
当前任务队列是 **Redis `BRPOP`，语义是"至多一次"** ——
`BRPOP` 取走即删除，**worker 在任务执行中途崩溃，这个任务就永久消失了**。
升级到"至少一次"需要 Redis Streams + 消费者组（`XREADGROUP` + `XACK` + `XAUTOCLAIM` 认领超时消息）。
我把这个缺口**写在了 `redis_queue.py` 的模块文档里**，而不是等面试官发现。

**落点**：`services/api/app/tasks/`（`queue.py` / `redis_queue.py` / `handlers.py`）
**可以展开**：`AIVideo` 项目用的是 RocketMQ（有事务消息和死信队列），
所以我可以对比讲"两种实现的投递语义差异" —— 这是真实经验，不是纸上谈兵。

## 五、架构与运维（#26–#31）——**P4 落地后基本变绿**

### #26 微服务拆分粒度与分布式事务 🟢
**问法**：为什么按业务能力而不是按技术分层拆？拆完跨服务的两个写操作怎么保证一致？

**答**：**按技术分层拆的反例**是 `llm-service` / `tool-service` / `prompt-service` ——
这会把一次对话变成 5 次网络往返，每个业务改动都要改 3 个服务，
是典型的**分布式单体**（付出了分布式的全部代价，没得到任何好处）。

**正例是 `rag-service`**：它有自己的数据（向量库）、自己的扩缩容曲线（CPU 密集）、
自己的故障语义（挂了可以降级为"不检索"），是一个**内聚的能力单元**。
判断标准是"**它能不能独立地被理解、部署和扩容**"。

**分布式事务**：本项目**没有做** outbox/Saga，原因是
"简历入库"和"建立索引"**共用同一份数据卷**，根本不存在双写 ——
**为不存在的问题加复杂度是最常见的过度设计**。
如果真要跨库，正确的顺序是：先尝试把两个写操作放进同一个服务（避免分布式事务），
做不到才用本地消息表 + 幂等消费（最终一致）——对求职场景允许秒级可见性延迟，
**不追求强一致**。

**落点**：`docs/01-architecture.md` 的 6.2/6.3 节（计划的拆分 vs 实际做了什么）

### #27 限流与熔断 🟢
**问法**：令牌桶和漏桶的区别？为什么在网关限流？LLM 上游挂了怎么降级？

**答**：**令牌桶**允许突发（桶里攒的令牌可以一次性用掉），
**漏桶**强制恒定输出速率。**真实流量天然是突发的**，所以令牌桶更实用。

**为什么在网关限流**：一次请求可能在服务内部放大成 10 次内部调用，
在入口限流能**在成本产生之前**挡住；在深层服务限流时，请求已经消耗了前几跳的资源。
但注意：**业务级配额（比如"每个用户每天多少 token"）必须在业务层做**，
因为只有业务层知道谁是"用户"。

**LLM 上游挂了怎么降级**：本项目区分了两种失败 ——
**网络/超时类**（可重试，带抖动退避）、**鉴权/参数类**（不可重试，立即失败）。
再往上一层是**熔断**：连续失败 N 次后直接快速失败，不再消耗超时时间。

**落点**：`services/api/app/core/resilience.py`（`TokenBucket` + `CircuitBreaker`）
**可以展开**：限流默认**关闭**，因为"没有标定过的阈值比没有阈值更危险"——
设错会直接拒掉正常用户，而且**不会报错，只会静默地少服务一部分人**。

### #28 可观测：trace_id 贯穿与链路追踪 🟢
**问法**：一次请求要经过 HTTP→Agent→LLM→Tool 四跳，怎么定位哪一跳慢？span 粒度怎么设计？

**答**：**`ContextVar` 而不是 thread-local** —— 这是本项目里一个具体的坑：
asyncio 中多个协程**共享同一个 OS 线程**，用 thread-local 存 trace id 会导致
**并发请求互相覆盖对方的 id**，表现是日志里的 id 张冠李戴，比没有 id 更糟。

**传播**：HTTP 入口接受并在响应里回显 `X-Trace-Id`，
调用下游服务时**透传同一个 header** —— 本项目实测"网关 → agent → RAG"三段能串成一条链路
（`verify_split.py` 里有一条专门验证 RAG 服务回显了上游 trace id）。

**span 粒度**：太细会被淹没（每次循环迭代都开 span），太粗没用。
本项目的粒度是**每一次工具调用**（带 `duration_ms`）和**每一次 LLM 调用**，
加上每步的序号 —— 这刚好是"定位哪一跳慢"所需的粒度。

**落点**：`services/api/app/core/telemetry.py`、`services/api/app/api/metrics.py`
**可以展开**：指标标签必须是**有界枚举**（工具名、模式），
**绝不能用 session id 或 URL 路径** —— 那会导致标签基数爆炸，
Prometheus 内存被吃光，这是监控系统最常见的自杀方式。

### #29 成本核算与归因 🟢
**问法**：流式调用怎么拿到 usage？多步 Agent 的 prompt 为什么随步数近似平方增长？单次对话成本怎么算？

**答**：流式下必须显式传 `stream_options: {"include_usage": true}`，usage 在**最后一个 chunk**，
否则一个 token 数据都拿不到。

**近似平方增长**：第 n 步要发送的是"系统提示词 + 全部历史 + 前 n-1 步的工具调用与结果"，
所以第 n 步的 prompt 长度 ≈ O(n)，总成本 ≈ O(n²)。
**这是 Agent 成本结构的核心特征**，也是 `max_steps` 是必需件而不是优化的原因。

**单次对话成本** = `Σ(prompt_tokens) × 输入单价 + Σ(completion_tokens) × 输出单价`。
本项目的 `Usage.__add__` 让每步的用量能累加，随 `done` 事件返回给前端。

**落点**：`services/api/app/llm/types.py`（`Usage.__add__`）、
`services/api/app/agent/loop.py`、`services/api/app/llm/client.py`（`include_usage`）

### #30 工具并发执行与失败隔离 🟢
**问法**：3 个互不依赖的工具串行 3T、并发 1T，为什么不一开始就并发？并发后一个失败怎么办？

**答**：**因为"互不依赖"这件事模型不保证**。模型可能在一个批次里同时请求
"读简历"和"基于简历内容检索岗位" —— 这两者有依赖，并发会拿到过期/缺失的结果。

**并发后的失败处理**是真正的问题：用 `asyncio.gather(return_exceptions=True)`，
**一个失败不取消其它** —— 因为其它工具的结果对模型仍然有价值。
但这要求每个 `ToolResult` 都携带自己的成功/失败状态，让模型自己判断
"我有 2 个结果和 1 个错误，够不够回答"。

**本项目的位置**：多智能体形态（`SupervisorAgent`）里已经实现了专家并发
（`asyncio.gather` + `Semaphore` 上限）。
但 **ReAct 主循环里同一批次的多工具调用仍是串行的** —— 这是一个**已知的待办**，
我把它明确写在了路线图里而没有假装已经做完。

**落点**：`services/api/app/agent/multi.py`（`Semaphore` + `as_completed`）

### #31 工程规范：lint / 类型 / 测试分层 🟢
**问法**：为什么要开 ruff 的 `ASYNC` 规则？`live` marker 的意义？怎么避免测试真的调大模型？

**答**：`ASYNC` 规则专门抓**异步函数里的阻塞调用**（`time.sleep`、`open()`、`requests`）——
这类问题的表现是"偶发卡顿"，很难靠 review 发现。

`live` marker 把"需要真实 API 调用（要花钱）"的测试隔离出来，
默认跳过，用 `-m live` 显式开启。**意义不只是省钱**：
它让"要不要真的调模型"变成**测试作者的一个显式决定**，而不是默认行为。

**怎么避免真调模型**：用**假 LLM**驱动 Agent 循环 ——
写一个按预设脚本返回 `tool_calls` / 最终回答的假客户端。
这样测试的是**我的循环逻辑**（正确的终止、正确的消息构造、护栏生效），
而不是模型的能力，而且完全确定性、零成本、毫秒级。

**落点**：`services/api/pyproject.toml`（ruff 规则集、mypy strict、pytest markers）、
`services/api/tests/`（18 个文件 / 590 用例）

**项目里的实证（这条能讲出深度）**：
我写过一条测试断言"子命令 `rag` 出现在 `dev.ps1` 文件里"，**它通过了**，
但实际执行 `dev.ps1 rag` 时被 PowerShell 直接拒绝 —— 因为 `ValidateSet` 没加。
教训是：**"断言某个符号存在"几乎不构成验证**，
要断言的是**让功能生效的那个具体结构**（改成断言 `switch` 标签 ⊆ `ValidateSet`）。
同类的还有一条：测试用 `sleep(0.01)` 同步两个协程的顺序 ——
单独跑必过、全量跑间歇失败，改成等 `Event` 后才稳定。
