# Legacy · 项目一页纸

> **验收方式**：找一个没参与过这个项目的人（同事/朋友）读这一页，5 分钟内能说清
> "这项目做什么、亮点是什么"。**做不到就改这一页，不是改读者的理解力。**
> 所以下面刻意不写实现细节，只写"它解决什么问题、凭什么可信"。

---

## 一句话

**一个求职/招聘 AI Agent：把"我的简历"和"目标岗位"放在一起，用带引用的检索增强生成回答匹配度、差距与改进方向。**

不是聊天机器人套壳 —— 核心是自己手写的 Agent 内核（ReAct / 规划 / 多智能体三种形态）、
一条带消融实验标定的混合检索链路，以及一套可观测、可降级、可拆分部署的后端。

---

## 它解决什么问题

求职者面对的真实困难不是"没有 AI 帮忙写简历"，而是：

| 真实痛点 | 现在是怎么解决的 | Legacy 怎么做 |
|---|---|---|
| 不知道自己**够不够格**投某个岗位 | 把 JD 丢给通用大模型问"我合适吗" | 先检索自己的简历与岗位库，**每个结论都带出处**（`[1] 简历.md · 专业技能`），可以自己核对 |
| 大模型会**编造**没写过的经历 | 反复换问法，越问越不确定 | 相关性闸门 + 明确拒答："资料里没有相关内容"，而不是硬编一个 |
| 简历太长，塞不进上下文 | 整份简历贴进提示词，token 随简历长度线性增长 | 按章节切分 + 混合召回，只把相关片段送进模型，**token 效率高一个数量级** |
| 问一句要等很久，还看不出在干什么 | 只能盯着转圈 | 前端实时渲染**工具调用时间线**：第几步、调了什么工具、耗时多少、返回是否被截断 |
| 一次分析要花多少钱说不清 | 没有任何计量 | 每轮对话的 token 用量随事件流返回，可折算成本 |

## 三个技术亮点（面试可直接展开）

### 1. 手写 Agent 内核，不引入 LangChain

**为什么**：框架把 ReAct 循环、工具协议、流式聚合都封装好了，但**出问题时你无法定位是哪一层** ——
工具参数解析错了、流式分片聚合错了、还是模型本身答错了？自己写一遍，这些都在自己的代码里。

代价也明确：要自己处理流式下 `tool_calls` 的分片重组（按 `index` 聚合而不是按 `id`，
因为 id 本身也是分片来的）、工具错误回灌、死循环检测。**这些代价就是学到的部分。**

产出：`Agent`（ReAct）/ `PlanAndExecuteAgent`（先出计划再执行）/ `SupervisorAgent`（主管路由到多位专家并发作答）
三种形态**共用同一套工具与护栏层** —— 两套实现迟早不一致，而那时你分不清差异来自"范式不同"还是"实现不同"。

### 2. 检索链路的每一步都有消融实验数字

不是"我觉得混合检索更好"，而是同一评测集、同一语料、同一个 k 跑出来的对比：

| 管线 | Recall@5 | MRR | NDCG@5 |
|---|---|---|---|
| ① 纯向量（基线） | 0.821 | 0.601 | 0.669 |
| ② 纯 BM25 | 0.798 | **0.685** | 0.718 |
| ③ 混合 RRF | **0.869** | 0.657 | **0.720** |
| ④ 向量 + 词法重排 | 0.821 | 0.685 | 0.717 |
| ⑤ 混合 + 词法重排 | 0.821 | 0.685 | 0.717 |

读表方式：**看每一步的增量，而不是只看最后一行多高**。混合 RRF 把召回推到最高（+0.048），
重排把排序质量推到最高（MRR +0.084）。而且⑤反而不如③的召回 —— 这个"负结果"也如实记录，
它说明重排在 top-k 截断时会丢掉部分召回。

### 3. 微服务拆分：先有接口边界，才有进程边界

拆分动机是**可测量的**，不是"架构上更优雅"：RAG 检索与索引重建都是纯 CPU 计算，
实测同时发生时在线检索 **P95 从 80.9ms 涨到 124.3ms（1.5×）、P99 从 86.8ms 涨到 169.0ms（1.95×）**。

拆的顺序更重要：**进程边界 → 接口边界 → 仓库边界**。第一步就同时搬代码的话，
出问题时你无法判断是"拆分设计有问题"还是"搬运时漏了什么"。

真正有技术含量的是第二步：原来工具层依赖 `len(retriever.chunks) == 0` 这个**隐式契约**，
它在同进程永远成立、一跨网络就彻底失效。所以先抽出显式接口（只有两个方法），
让工具只依赖接口，**然后**才加远程实现。做完前两步，第三步几乎免费。

| 指标 | 数值 | 怎么复现 |

| 检索质量（公开评测集，14 条查询） | Recall@5 0.821 / MRR 0.685 / NDCG@5 0.717 | `python scripts/eval_rag.py --run --sample` |
| 消融对比 | 见上表 | `python scripts/eval_rag.py --compare --sample` |
| 压测（8 并发，单机本地） | `/healthz` P95 15.6ms；RAG `/context` P95 80.9ms | `python scripts/loadtest.py --contention` |
| 熔断效果 | 熔断后 20 次调用 **< 50ms**（否则需 1.0s） | `pytest tests/test_resilience.py` |

⚠ **必须一起说的前提**：压测是**单机本地**数据（无网络延迟、无跨可用区、无真实流量分布），
且压测进程与被测服务同机，并发越高延迟越偏悲观。**不能当作生产容量结论。**

## 诚实的边界（这一节比亮点更重要）

面试里**主动说出短板**是加分的，被追问出来才是减分：

| 没做的 | 为什么 | 如果要做到会怎么做 |
|---|---|---|
| 消息队列的**至少一次**语义 | 当前用 Redis BRPOP，是**至多一次** —— worker 崩溃会丢任务 | Redis Streams + 消费者组（XACK / XAUTOCLAIM）+ 内容 hash 幂等键 + 死信队列 |
| 向量库换 pgvector | 语料只有几十块，numpy 暴力检索足够了 | 接口已经留出（`VectorStore`），换实现不影响上层 |
| 真实的多租户鉴权/限流 | 单用户作品集项目 | 网关层统一鉴权 + Redis 令牌桶，现在限流已按会话实现但默认关闭 |
| `docker compose up` 实跑 | 本机 Docker 未运行 | compose 已写好并被测试静态校验（服务名/端口/必须成对的环境变量） |
| 千万级向量检索 | 没有那个量级的数据 | 现在做的是"小语料做对"，不是"大语料堆机器" |

**另一条底线**：评测集只有 14 条查询，样本量小，指标波动大。
把它当作"改动前后有没有劣化"的**回归门禁**是合适的，
当作"这个系统的检索能力有多强"的结论是**过度解读**。
