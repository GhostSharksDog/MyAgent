# 现场演示脚本（3 分钟）

> **验收标准**：**断网状态下也能跑完**。
> 这不是"尽量"——`scripts/verify_demo.py` 会把 LLM 地址指向一个**不可达端口**，
> 然后断言完整事件流仍然产出。跑不过就说明离线兜底是假的。

---

## 零、演示前 60 秒检查（**不要跳过**）

```powershell
# 1. 启动离线演示模式（不调用模型，重放录制好的事件流）
.\scripts\dev.ps1 demo

# 2. 另开一个终端，验证离线能力（会把 LLM 指向不可达端口）
.\scripts\dev.ps1 verify-demo
```

**必须确认 `/healthz` 的 `demo_replay` 字段不是 `off`**：

```powershell
(Invoke-WebRequest http://127.0.0.1:8000/healthz -UseBasicParsing).Content
# 期望看到： "demo_replay":"1081 个事件，录制于 ...，模型 deepseek-chat，问题：岗位库里..."
```

> ⚠️ **这一步是整套演示里最容易被跳过、也最致命的**。
> 如果 `demo_replay` 是 `off`，说明回放在配置里没生效 ——
> 那演示时就会**真的去调模型**，网络一慢就是一次无法解释的等待。
> 这个字段存在的唯一理由就是让这种错误在演示前暴露。

如果要用真实链路演示（网络与额度都可靠时）：

```powershell
.\scripts\dev.ps1 serve   # 正常模式；/healthz 的 demo_replay 应为 off
```

## 一、演示流程（3 分钟，按秒分配）

### 0:00–0:20｜一句话说清项目

> "这是一个求职 Agent。它解决的**具体问题**是：我以前判断'我够不够格投这个岗位'，
> 只能把 JD 丢给大模型问 —— 它会编造我没写过的经历，而且我无法核对。
>
> 这个系统的做法是：先检索我自己的简历和岗位库，**每个结论都带出处**，
> 查不到就明确说查不到。"

**动作**：打开前端页面（`cd apps/web; pnpm dev` → `http://localhost:5173`）。

### 0:20–0:40｜提问，指出"流式"这件事

**输入**：`岗位库里有哪些大模型应用方向的岗位？它们分别要求什么技术？逐条列出并标注出处。`

> "注意文字是**逐字出现**的，不是等完整答案再一次性渲染 —— 这是 SSE 流式。
> 前端只依赖 React 和 React DOM，SSE 分帧器是我自己写的。"

### 0:40–1:30｜**重点**：工具调用时间线（这是整个演示的核心）

**动作**：指向工具卡片区域。

> "这里是关键。模型没有直接回答，它先做了两次工具调用 ——
> 卡片上能看到：**第几步、调了什么工具、耗时多少毫秒、返回是否被截断**。
>
> 这就是我为什么自己手写 Agent 内核而不用 LangChain：
> 用框架的话，'模型答错了'、'工具参数解析错了'、'流式分片聚合错了'，
> 这三种失败**看起来是一样的**。自己写，它们分别在我不同的文件里。"

**如果要展开**（有技术背景的面试官）：

> "工具调用这里有个协议细节：流式下 `tool_calls` 的 `arguments` 是**逐字符分片**到达的，
> 聚合必须按 `index` 而不是按 `id` —— 因为 `id` 本身也是分片来的。
> 按 id 聚合会把同一次调用拆成多次。"

### 1:30–2:10｜答案里的引用（RAG 的"可核对"）

**动作**：指向答案里的 `[1]` `[2]` 标注。

> "每个结论后面都有出处编号，对应上面的检索片段。
> **这是 RAG 和'问大模型'最本质的区别：用户可以自己核对。**
>
> 而且检索不到的时候它不会编 —— 我问一个简历里没有的东西试试。"

**输入**（挑一个语料里确实没有的）：`我在字节跳动的工作经历是什么？`

> "它会明确说'资料里没有相关内容'，并告诉我换个问法或扩大范围。
> 在求职场景里这一点尤其重要 —— 用户会**依据这个结论做决策**（投不投这个岗位），
> 编造一个'你有相关经验'的代价远大于说'没找到'。"

### 2:10–2:40｜成本与可观测

**动作**：指向前端的 token 用量显示。

> "每轮对话的 token 用量随事件流返回，可以折算成本。
> 这里有个 Agent 特有的成本特征：**多步对话的 prompt 随步数近似平方增长** ——
> 因为第 n 步要发送全部历史加上前 n-1 步的工具调用结果。
> 所以 `max_steps` 和死循环检测是**必需件而不是优化**：
> 没有它，一个把工具当'思考'用的模型会无限调用，单个请求就能烧掉一个月额度。"

### 2:40–3:00｜收尾：一句话给出深度

> "如果要我用一句话总结这个项目学到的东西：
> **不是'我会用 AI 框架'，而是'我知道 AI 系统在哪里会坏，以及怎么发现它坏了'。**
>
> 比如检索质量我是用消融表测的 —— 混合召回把 Recall@5 从 0.821 提到 0.869，
> 重排把 MRR 从 0.601 提到 0.685。而且我保留了一个负结果：
> 混合加重排反而不如纯混合的召回，这说明重排优化的是排序而不是召回。"

## 二、离线兜底：为什么它是真的

不是"录个屏放一下"，而是**后端真的在按事件流推送**：

| | 实现方式 |
|---|---|
| 数据源 | `app/demo/replay.py` 重放录制的事件流 |
| 端点 | **完全相同**的 `POST /api/chat/stream` |
| 序列化 | **完全相同**的 `AgentEvent.to_sse()` |
| 分帧 | **完全相同**的 SSE 帧格式（含 `ping` 心跳） |
| 区别 | 只有事件的来源 |

所以演示时即使有人打开 DevTools 看网络请求，看到的也是真实的 SSE 流 ——
**因为它就是真实的**。唯一"不真实"的是事件来自录制而不是当场推理。

**为什么回放放在后端而不是前端 mock**：前端 mock 只能骗过 UI，
而且它无法证明"后端真的在流式推送"这件事。

### 验证方法（可复现）

```powershell
# 把 LLM 指向不可达端口，再启动回放模式
$env:LLM_BASE_URL = 'http://127.0.0.1:9/v1'
$env:DEMO_REPLAY_FILE = 'demo/transcript-public.json'
.\scripts\dev.ps1 demo

# 另一个终端
.\scripts\dev.ps1 verify-demo
```

**实测结果**（本项目真实输出）：


## 三、重新录制

录制会抓到 **`search_knowledge` 的原始返回** —— 也就是简历原文（姓名、电话、学校、公司）。
所以脚本内置了 PII 闸门，**写入之前**先扫描，命中就**拒绝写出**。

```powershell
# 默认输出到 data/demo/transcript.json（data/ 已被 gitignore）
.\scripts\dev.ps1 record-demo

# 录一份只问公开岗位库的（PII-free，可以提交进仓库让别人也能跑）
python scripts/record_demo.py --out demo/transcript-public.json `
  --question "岗位库里有哪些大模型应用方向的岗位？它们分别要求什么技术？逐条列出并标注出处。"
```

实测闸门确实拦住了（第一次录制）：

```
共录到 803 个事件
  token 用量：{'prompt_tokens': 6387, 'completion_tokens': 897, 'total_tokens': 7284}

!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
PII 检查未通过，**拒绝写出文件**
!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!
命中：[通用模式] 手机号、邮箱
      [具体词]  姓名、学校、公司名、GitHub 用户名、竞赛名、项目名
```

> **为什么这里只写"命中了哪一类"，不写命中的原文**
>
> 第一版这段文档里**贴了闸门的完整命中列表** —— 也就是把闸门刚刚拦下来的
> 姓名、手机号、学校、公司名原样写进了一个**要提交的文档**。
> 那份文档自己的下一段还写着"报告时只输出命中了什么模式，不打印上下文"。
>
> 这是个很典型的错误：为了"证明工具有效"，把工具拦下的敏感数据搬到了另一处。
> **证明一个防护有效，不需要公开它保护的东西。**
> 只要说明"它拦住了 N 类、以及拦住之后的处理流程"就够了。
>
> 这类错误的可怕之处在于它是**自相矛盾却不自检**的：
> 文档的两段互相打脸，而没有任何机制会把这件事报出来 ——
> 直到有人去扫历史。

> **为什么闸门必须在写入之前**：这个文件一旦被误提交，PII 就**永久进入 git 历史** ——
> 删掉文件删不掉历史，只能改写历史（force push + 所有协作者重新克隆）。
> 代价太大，所以要在源头挡住。而且**没推送之前改写历史是免费的**：
> 没有协作者、没有 clone、没有 PR，改完 hash 变了也无所谓 ——
> 这个窗口一旦错过就再也没有了。
>
> **具体词表放在哪**：不能硬编码在脚本里（那样检测器自己就成了泄露点），
> 要放在 gitignore 覆盖的文件里（本项目是 `data/pii-terms.txt`）。
> 脚本内置的只有**通用格式**（手机号/邮箱/身份证），那些是格式不是个人信息。
>
> **推送前的最后一道**：`scripts/scan_history_pii.py` 扫的是
> **所有提交的所有 blob**，而不是当前工作区 ——
> 因为 git 是只追加的，删掉文件不等于它从历史里消失。

## 四、演示最容易翻车的三件事（以及这里怎么防）

| 翻车点 | 表现 | 这里的防护 |
|---|---|---|
| **网络/额度不可用** | 演示到一半卡住或报错 | 离线回放模式，实测 0.6 秒产出完整事件流 |
| **回放配置没生效，悄悄走了真实链路** | 演示时出现无法解释的等待 | `/healthz` 的 `demo_replay` 字段；**演示前必须确认不是 `off`** |
| **回放文件是旧版本事件模型录的** | 前端时间线渲染到一半停住，看起来像前端 bug | 加载时逐条还原成 `AgentEvent`，格式不符**立即明确失败**并指出第几条 |

第三条尤其值得讲：如果只做 `json.loads` 就把数据交给前端，
排查方向会一路跑到前端去，而真正的问题是**录制文件过期了**。
**让格式问题在最靠近它的地方、以最清楚的方式失败**，是这类"跨版本契约"的通用做法。
