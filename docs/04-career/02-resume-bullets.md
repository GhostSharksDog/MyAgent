## 一、先决定"这个项目在简历上补什么"

写之前必须先看清已有的东西，否则会把新项目写成一个"重复已有经历"的项目 —— 那是最亏的写法。

| 能力 | 已有经历里的证据 | JobPilot 能补吗 |
|---|---|---|
| 消息队列 / 异步解耦 | AIVideo：RocketMQ + 线程池，60s+ 接口 → 50ms 以内 | ❌ 已经有了，而且更强（RocketMQ 事务消息、死信） |
| 缓存与一致性 | AIVideo：Redis + Cache Aside；实习：ClickHouse 物化视图生命周期 | ❌ 已经有了 |
| 分布式锁 / 限流 | AIVideo：Redisson 分布式锁 + 全局限流 | ❌ 已经有了 |
| 大数据 / 实时链路 | 实习：Flink CDC + Debezium，MySQL/PG → ClickHouse 一致性 100% | ❌ 已经有了 |
| 亿级数据检索 | 实习：ClickHouse 物化视图 + Bitmap 位图索引，亿级实体标签圈选 | ❌ 已经有了（而且是更难的那个） |
| 全栈 / 前端 | 实习：Next.js + React + TS；AIVideo 前端 | ⚠️ 有，但 JobPilot 前端可以展示"流式状态机"这种新东西 |
| **大模型 / RAG / Agent** | **无** | ✅ **这是唯一的空白，也恰好是目标岗位的核心要求** |
| **评测驱动 / 量化门禁** | 无（"数据一致性 100%"是结果，不是门禁） | ✅ 空白，而且能展示工程方法论 |
| **可观测 / 链路追踪** | 无 | ✅ 空白 |
| **微服务拆分取舍** | 有 Docker Compose 编排经验 | ⚠️ 编排有，**拆分决策与代价**没有 |

**结论**：JobPilot 这一条必须**先讲 AI 工程，再讲工程方法论**；
MQ / 缓存 / 限流在 JobPilot 里也存在，但**不要当作亮点写** —— 那是重复，而且你的 AIVideo 讲得更好。

**唯一值得提的衔接点**是"同一个工程直觉在不同场景下的延伸"，比如：
`AIVideo 用 RocketMQ 把 AI 长任务从请求路径摘出去` → `JobPilot 把重建索引摘出去`
这是同一个人在同一条思路上往前走，而不是两个互不相关的项目。

## 二、简历条目（可直接粘贴，含数字溯源）

### 版本 A：完整版（个人项目栏目，5 条）

> **JobPilot · 求职/招聘 AI Agent** ｜ 个人项目 ｜ Python (FastAPI) + React 19 + TypeScript
>
> **背景**：求职者判断"我够不够格投这个岗位"时，只能把 JD 丢给通用大模型问 —— 模型会编造没写过的经历，
> 结论无法核对，长简历塞不进上下文，而且看不出它到底查了什么。
>
> **动作与结果**：
>
> - **手写 Agent 内核替代 LangChain**：自己实现 ReAct 循环、工具协议与流式分片聚合（按 `index` 而非 `id`
>   聚合 `tool_calls`），在同一套工具与护栏层上扩展出**规划型**与**多智能体主管-工人**两种形态；
>   三种形态共用工具层避免行为漂移。输出 **5 个可被模型调用的工具、19 个 HTTP 端点**，
>   后端 **590 个测试通过**。
> - **搭建带引用标注的 RAG 检索链路**：章节切分 → TF-IDF 稠密召回 + 手写 BM25 倒排 → RRF 排名融合 →
>   词法重排 → 相关性闸门。每个回答都带 `[1] 出处` 标注可人工核对，检索不到时**明确拒答**而不是编造。
>   公开评测集上 **Recall@5 = 0.821、MRR = 0.685、NDCG@5 = 0.717**。
> - **用消融实验而非直觉标定参数**：同一评测集/语料/k 下跑 5 条管线对比 ——
>   混合 RRF 把 Recall@5 从 0.821 提到 **0.869（+0.048）**，词法重排把 MRR 从 0.601 提到 **0.685（+0.084）**；
>   同时如实记录"混合+重排反而不如纯混合的召回"这一**负结果**，据此把重排定位为排序优化而非召回优化。
>   把指标写成**回归门禁**（低于 0.74/0.60/0.64 则 CI 失败），防止后续改动静默劣化。
> - **按"接口边界先于进程边界"的顺序拆分微服务**：先抽出显式检索接口（2 个方法），再实现 HTTP 远程版本，
>   最后才拆进程（`api` / `rag` / `worker` 三角色）。拆分动机用数据说话：
>   检索与索引重建同占 CPU 时，在线检索 **P95 从 80.9ms 涨到 124.3ms（1.5×）、P99 从 86.8ms 涨到 169.0ms（1.95×）**。
>   用 `ASGITransport` 让真实客户端调真实服务端做**契约测试**，填补"单体单测"与"线上联调"之间的缺口。
> - **可观测与韧性**：`ContextVar` 实现 trace id 跨 HTTP → Agent → LLM → Tool → 下游服务五跳贯穿
>   （刻意不用 thread-local —— asyncio 共享线程）；手写指标注册表暴露 Prometheus 与 JSON 两个端点；
>   熔断器让下游故障时 **20 次调用合计 < 50ms**（未熔断则需 1.0s），并明确区分"故障"与"业务状态"
>   （知识库为空不算失败，否则会把健康服务误判为故障）。

### 版本 B：精简版（一页简历用，3 条）

> **JobPilot · 求职/招聘 AI Agent** ｜ 个人项目 ｜ Python + React 19 + TS
>
> - **手写 ReAct Agent 内核**（不依赖 LangChain）：自定义工具协议与流式 `tool_calls` 分片聚合，
>   同层扩展出规划型与多智能体主管-工人形态；**590 后端测试 / 58 前端测试**。
> - **RAG 检索链路 + 消融标定**：章节切分 + 稠密/BM25 混合召回 + RRF + 重排 + 相关性闸门，
>   回答带出处标注、检索不到即拒答；公开评测集 **Recall@5 0.821 / MRR 0.685 / NDCG@5 0.717**，
>   消融证明混合召回带来 **+0.048 Recall**、重排带来 **+0.084 MRR**；指标已做成 CI 回归门禁。
> - **微服务拆分与可观测**：按"接口边界先于进程边界"拆出独立检索服务与 worker，
>   实测检索与索引重建争抢 CPU 时 **P95 放大 1.5×**；实现 trace id 五跳贯穿、Prometheus 指标与熔断降级。

## 四、写法上的四条纪律

**1. 每个数字都要能当场复现。**
"性能提升了 3 倍"在面试里经不起追问 —— 怎么测的？多大数据量？并发多少？
答不上来的数字比不写更糟：它会让面试官怀疑**其它数字也是编的**。
所以上面每个数字都配了命令。

**2. 主动写上负结果。**
"混合 + 重排反而不如纯混合的召回"这种话**要主动说**。原因：
- 它证明你真的读了表，而不是挑最好看的数字
- 它证明你知道重排的作用域是排序，不是召回 —— 这是理解深度的直接证据
- 面试官如果自己发现了这个"矛盾"而你没提，性质就变了

**3. 不要把已有能力重复写。**
MQ、缓存、分布式锁你在 AIVideo 和实习里已经讲得更好。
在 JobPilot 条目里重复一遍，只会让面试官觉得你只有一个套路。

**4. 把"没做"的也写进准备里。**
消息队列的至少一次语义（当前是至多一次，worker 崩溃会丢任务）、
pgvector、多租户鉴权、`docker compose up` 实跑 —— 这些都要能被问，
**而且要能立刻给出"如果做我会怎么做"**。诚实的边界管理比硬答安全得多。

## 五、把两段经历缝起来（面试时的一句话衔接）

面试官常问"这两个项目有什么关系"。**不要答"都是练手"**，可以这样接：

> AIVideo 解决的是"AI 长任务把同步请求堵死"，做法是用 RocketMQ 把任务摘出去 ——
> 那里的"任务"是一段完整业务，异步边界很清楚。
>
> JobPilot 里遇到了同一类问题的**更细粒度版本**：Agent 的一次回答内部有 3~5 次工具调用，
> 中途一次检索就可能要几百毫秒，而且它**不能异步** —— 模型在等这个结果才能继续决策。
> 所以异步化在这里不适用，改用的是熔断（下游挂了就快速失败而不是硬等）和
> 把 CPU 密集的索引重建拆到独立进程。
>
> 我的体会是：**异步、熔断、拆进程解决的是同一类问题的不同阶段**，
> 分不清"该等还是该失败"的时候，就容易把简单问题做成分布式问题。

这段话的价值在于：它展示的不是"我做过两个项目"，而是
**在同一个工程直觉上的演进，以及知道每种手段的适用边界** ——
后者恰恰是 JD 第 4 条"分布式+微服务+MQ+缓存"真正想考的东西。
