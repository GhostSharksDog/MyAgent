feat(P4): 拆分 RAG 检索服务与独立 worker 进程，并加跨进程验证与拓扑门禁

拆分的三个具体动机（不是架构洁癖）：
- RAG 是 CPU 密集而 agent 是 IO 密集，同进程时重建索引会抢 agent 的 CPU
- 两者伸缩比不同，绑在一起只能整体扩容
- 故障隔离：RAG 崩了不该让整个对话服务不可用

关键设计：先把隐式契约变成显式接口，再加远程实现
- 新增 rag/backend.py：KnowledgeBackend 协议（只有 context/stats 两个方法）
- 原来 KnowledgeSearchTool 依赖 len(retriever.chunks)==0 这个隐式约定，
  它在同进程永远成立、一跨网络就失效，是拆分最典型的翻车点
- 工具层改为只依赖接口后，本地/远程实现抛出的异常类型完全一致，
  工具不需要知道自己在走进程内调用还是 HTTP
- 「知识库为空」跨进程后调用方无法自行判断，必须由服务端用 503 说出来，
  否则「该去准备简历」和「该换个问法」会被压成同一句误导性提示

新增：
- app/rag_service/main.py：独立检索服务（/retrieve /context /reindex /healthz /metrics）
  接口刻意粗粒度：细粒度接口会把一次检索变成多次网络往返
- app/worker_main.py：独立 worker，backend!=redis 时退出码 2 明确报错，
  而不是对着空队列静默空转
- docker/Dockerfile + docker-compose.yml：单镜像多入口（三服务共享代码，
  差异只有启动命令），非 root 运行，data/ 挂载而非打包（简历属于个人信息）
- scripts/verify_split.py：去 RAG 服务自己的指标端点确认请求计数真的涨了，
  因为「有结果 != 请求真的到达了那个进程」

修复：
- httpx.ConnectTimeout 同时继承 TimeoutException 与 TransportError，
  异常分支写反会把「服务没起来」报成「服务过载」，排查方向完全错误
- /healthz 只读配置、不探活下游：让健康检查依赖下游会导致级联故障
- TASK_RUN_WORKERS_IN_API=false 配进程内队列 = 任务永远 pending，
  改为启动即拒绝并说明正确组合

可观测性：/healthz 与 /api/meta 暴露 rag_backend / task_backend /
task_workers_in_api —— 三者的共同点是配错了不报错，只会静默换拓扑

测试 528 -> 563：
- TestContractAgainstRealServer 用 ASGITransport 让真实客户端调真实服务端 app，
  填上「单体单元测试」与「线上联调」之间的缺口（两端各自 mock 时，
  字段名不一致会同时全绿）
- TestComposeTopology 把关编排层那些必须成对出现的变量
  （RAG_SERVICE_URL 主机名必须真实存在、api 与 worker 消费关系必须互补）

本机坑（已加回归门禁）：
- scripts/*.ps1 必须带 UTF-8 BOM。本机 PowerShell 是 5.1，无 BOM 时按 GBK 解码，
  而 GBK 解码 UTF-8 中文会吞掉后续字节（常是换行或引号），
  导致行号错位、语法树崩溃，报错位置却指向一句无辜的中文注释
